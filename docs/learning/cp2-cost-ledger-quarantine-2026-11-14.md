项目授权 cap 是 `$0.50`，不是供应商余额。版本控制中没有原始 `reports/` CSV，也没有 `budget-ledger-v1.json`；无法从现有仓库重建运行账单或确认当前余额。

旧学习记录称 73 个 CSV 有 92 个去重 run，估算 `$0.484753`，另加 partial `$0.001120`，并写余量 `$0.014127`。原始 CSV 和 partial 文件未纳入版本控制，无法复算。该数值只是旧文档中的历史估计，不能视作已核实消费、余额或可调用额度。

另一份 CP-1 学习记录列出 4 个运行估值，合计 `$0.014091`。没有 run ID，无法确认它们是否已包含在旧的 92-run 汇总中，因此不能再加一次。CP-4 的 `$0.36` 是六次试验的计划预留；记录显示预检未完成，不能算作消费或当前活动预留。CP-2 全量配对的 `$1.731456` 被预算门禁阻断，也不是消费。

## 账本行为

- CSV 行优先用稳定 `run_id` 去重；无 run ID 时才用稳定 `request_id`。同一身份重复出现只计一次；冲突时取较大值并记录冲突数。
- 同时缺失 `run_id` 与 `request_id` 的行进入隔离区；不按文件路径或 case 行号制造 ID，不计入已知用量。
- partial 文件一律进入 `unknown_overlap_quarantined`，不与 CSV 汇总相加。
- 余额状态固定为 `unknown`，直到外部余额与累计 usage 都有可核验证据。估算余量和可用额度均返回 `null`。
- 没有原始 CSV 时标记 `missing_raw_csv`，仍保持 fail-closed。

`tests/test_cp2_benchmark.py` 中纯合成回归覆盖重复 run、重复 request、缺失 ID、与 CSV 同 run 的 partial，以及原始 CSV 缺失/余额未知。测试数据只写到 pytest 的系统临时夹具，不读项目 `.tmp`、`.env` 或真实报告。

未访问供应商账户，因此没有余额证据；未调用模型。4 题试跑的 `$0.2308608` 是峰价最坏费用预留，不代表当前余额，也没有被本账本标记为已批准或已保留。
