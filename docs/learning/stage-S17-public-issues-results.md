## 失败分析

预算护栏没有过度调用模型，也没有提前提交不完整补丁。它保留了两次后续调用的测试/收尾预算，但本轮给每个任务只设 25k Token：

- 仓库规模配置出 7,500 字符上下文上限；完整工具定义本身约占 1,939 Token 的预留估算。
- 每次请求需要约 2.8k–5.2k 输入 Token。四次请求后，实际累计约 13k–14k Token。
- Agent 当时需给一次测试决策和一次最终收尾保留约 9,390 Token。剩余预算已不足以同时容纳下一次约 5k 的当前请求和这两项保留，于是安全停止。
- 三条轨迹都在第 4 步停止；模型主要搜索和读取源码，尚未调用 `apply_patch`。Flask 任务搜索了 3 次；urllib3 #3649 读取了 10,018 字符；#3700 搜索两次。三项的 `run_tests_calls` 都为 0。

这是**实验配置预算不足**，不代表模型产出的修复失败，也不能代表它已理解并修复问题。S17 暴露后不可再作为未见 holdout 重跑。下一批真实任务须在冻结前设置足以包含上下文、测试和最终回复的 Token 上限，并继续逐任务限额；S3 的阶段记录显示，复杂任务 25k 会停止，而 60k 配置曾完成发票任务，但不能据此断言本批任务一定通过。

## 自动化修复基准对照

[SWE-agent](https://github.com/SWE-agent/SWE-agent) 的输入是 GitHub issue，目标是直接在真实 GitHub 仓库内尝试修复；其 README 目前说明主力开发已转向 mini-SWE-agent，并推荐新用户采用后者。[OpenHands Benchmarks](https://github.com/OpenHands/benchmarks) 提供 SWE-Bench、SWE-Bench Pro 等标准化评测管线，并固定 Agent SDK 子模块提交以提高可复现性。

CodePilot 已具备一些相同的评测纪律：issue 关联、固定源码摘要、Docker 断网测试、隐藏验收、运行轨迹、Token/费用/耗时统计，以及外部 Git 仓库审批后写回。项目目录外仓库的真实 CLI 写回流程已在 [S3 阶段记录](stage-S3-project-context.md) 记录；本次完整 `tests` 测试也覆盖 CLI 写回、审批与过期写回拒绝。

当前与这些项目仍有明显差距：没有官方 SWE-Bench 任务格式和 harness，没有大样本、多模型、多次运行的置信区间，也没有与 SWE-agent 或 OpenHands 在相同容器、模型、预算和任务上做对照。本批三项全因预算不足而中断，结果只支持“安全地停止并留下可分析轨迹”，**不支持修复能力达标、生产可用或追平其他 Agent 的结论**。
